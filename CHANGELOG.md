# Changelog

Podaro Community's releases, newest first. Each entry says what the release does and what it deliberately does not.

Interface changes live in the interfaces: the schemas under `schemas/` carry their own dated, additive changelog lines in their `$comment`. This file records releases.

## v0.1.0 — unreleased: pending the acceptance run on a clean host and the `v0.1.0` tag

**The MVP: one perfect lab, one host, the whole loop.** A YAML definition becomes a running lab whose readiness is *proved* — baseline checkpoints against live system state, not containers-up — served to any browser from one Linux VM through a single TLS port, with the products, the instructions and the verification in one page. The lab it ships is all open source and fits a 4 GB host.

Installed by `install.sh` from the release tarball: run once under `sudo` it creates the dedicated `podaro` account (home `/opt/podaro`), prepares the host line by line — subordinate IDs, lingering, Podman if you say yes — and then installs as that account: one binary that carries the engine, the CLI, the console and the starter catalog, run as the account's systemd *user* service. The engine never runs as root. Run as the account instead, the script performs no privileged act, and `podaro doctor` diagnoses and prescribes but never operates: the commands root would have to run are printed for you. The gateway listens on 7777 by default. The installer also asks whether to export Podaro's own logs over the HTTP Event Collector protocol and, on a yes, writes the `observability` block, keeps the token in a `0600` file, restarts the engine and probes the destination before it finishes; the default is no. The console login defaults to `podaro-admin`, distinct from the `podaro` Linux account, and a last question creates the open-source lab as `intro` and prints every hostname a browsing machine must resolve for it. A `sudo -iu podaro` shell works as the documents promise: the installer's block in the account's profile supplies the session variables such a shell lacks, and the engine sets them for its own `systemctl --user` calls regardless; a `destroy` whose `podman rm` is refused by the rootless network helper once is retried once. A checkout of the repository builds that same release with `./build.sh`: every missing tool is a row with its remedy, Go is installed only when `--yes` says so, and `--install` hands the package to the installer; run in a checkout with no binary beside it, `install.sh` stops and names the build. `podaro system status`, `start`, `stop` and `restart` drive the service from any shell the account gets — `status` probes the engine behind the unit and exits 0 only when both are up — and `podaroctl`, the tarball's fourth entry, runs any `podaro` command as the account from an administrator's own shell (`sudo /opt/podaro/podaroctl status`; on PATH as a root-owned copy if you ask the installer).

**What this release does**

- **The loop.** `up` → `status` → `verify` → `seed` → `reset` → `destroy`, each streaming the seven-stage ready ladder in the same grammar the console renders. Create validates, plans, creates, initialises, seeds and verifies; interrupting the CLI detaches from the job rather than killing it; `kill -9` and a reboot are survived — the engine reconciles containers back to their prior stage and re-verifies baselines, and says that it did.
- **Ready means verified.** Checkpoint *classes*: baselines gate `ready` and the pre-flight; objectives are the learner's work, expected red at create, and never block readiness. An objective already green at create is reported as `PDR-W101` rather than counted as an achievement.
- **Verification that queries products.** Built-in adapters `http` (status, body, JSON path — a product's own API asked), `container` and `attest`, plus the **exec adapter**: your own digest-pinned container as the judge, run on the lab network under five walls, and reachable under a module's own alias. Built-in generators `http-requests` and `web-logs`, and exec generators beside them. New products need no engine release.
- **The starter lab.** `grafana-prometheus-intro` — Prometheus scraping itself and Grafana, Grafana with its Prometheus datasource provisioned — all open source, in 4 GB: four baselines that gate `ready`, the deterministic `query-load` seed, and the `first-dashboard` playbook, whose two objectives (the traffic you drive, a dashboard titled *Lab Overview* that Grafana's own API confirms) are red at create and yours to turn green. It is the whole starter catalog, and it runs no proprietary software.
- **The licence gate, for templates you author.** A template that declares a EULA is refused with `428` until its terms are accepted — per create, explicitly, by typing the licence id, never defaulted — and the acceptance is recorded in evidence. Proprietary images are referenced and never redistributed. CI proves the gate on a first-party fixture under a fictitious id, and `PDR-W101` on another.
- **The contracts.** Templates, modules, playbooks and checkpoints are `lab.podaro.dev/v1alpha2` (the schemas under `schemas/`); the engine still reads `v1alpha1` documents, as frozen history identical in meaning, and `lab init` writes `v1alpha2`. The API stays `v1alpha1` and the exec contract v1.
- **The console**, server-rendered fragments over the same handlers as the JSON API (htmx + Alpine, vendored and pinned, zero external requests — fonts included): Overview with the full ladder and one start-here card, product tabs embedded through the gateway or an honest **Open ↗** card, the playbook rail in **Guided** (soft gating, hints, persisted progress) and **Presenter** (speaker notes, confidence lights, nothing that pops), an Evidence scoreboard, audited credential reveal, and the reset dialog's two columns. A ladder that falls back from ready says so: the condensed bar turns amber and the fall is announced once, in words, to a screen reader.
- **Attendee access links.** `podaro access create` issues an expiring, revocable, hashed-at-rest credential whose join opens a session bound to one lab, with a grant fixed in the engine: no destroy, no reset, no logs, no other lab. Completion evidence carries the attendee's name.
- **Evidence** as an append-only journal: JSON, JUnit for CI, and a standalone HTML report built to be forwarded — with no secret values, no hostnames and no addresses in it.
- **Secrets that never appear.** Generated per instance, `0600`, revealed only through the audited console action, absent from logs, CLI output, evidence, plans and exports. A scripted scan across every run in CI asserts it.
- **Observability export, off by default.** Podaro's *own* logs, metrics and traces to destinations *you* configure — per-signal `otlp`, `http` or `hec` (traces OTLP-only), the same redaction filter on the way out, credentials in `0600` `token_file`s, `podaro observe status|test` and a doctor posture row. **Vendor telemetry is zero, ever:** nothing is sent to the project or to anyone, not even opt-in.
- **Operability.** `podaro explain <PDR-code>` reads the registry inside the binary, so it works when the engine does not; `podaro logs` is redaction-filtered and follows; `podaro system upgrade` asks the project's releases, `https://github.com/JeremiahJRRoss/podaro/releases`, or a mirror you filled yourself on a host with no route out, verifies a release's checksum before replacing anything, backs the state up first, and migrates forward-only.
- **Authoring.** `podaro lab init --from <template> ./my-lab` scaffolds (as `v1alpha2`), `lab validate` reports schema, referential and policy findings at `file:line`, `lab plan` prints what create would do — byte-identically, twice. An instance created from a directory is an *authoring* instance: it tracks your files and flags its evidence as authoring work. Modes never switch in place.
- **The licence, the notices and the source, on every copy.** `podaro legal` prints the licence (`AGPL-3.0-only`), the project's two statements from `NOTICE`, the offer of the running binary's exact source — its release tag in the repository the binary names, or, for a development build, that no tag holds it — where releases are published and how to verify one against `SHA256SUMS`, the name policy and the third-party components, offline from the binary; `--licenses` prints every licence text it carries. The console's `/legal` page shows the same to anyone who can reach the console, signed in or not — an attendee and a visitor at the sign-in page included — linked from every page's footer. The tarball carries `LICENSE`, `NOTICE`, `TRADEMARKS.md`, `THIRD-PARTY-NOTICES.md`, `LICENSES/`, `SOURCE-AND-BUILD.md` and `RELEASE-MANIFEST.json` beside the binary, the installer puts the notices beside the installed binary, and `system install` writes them to `~/.local/state/podaro/legal/` for a binary that came without the tarball. An independently named build is one build flag away (`internal/brand`), and changes the display name and nothing else.

**What this release deliberately does not do**

- **No portable bundles.** `podaro export` and `up --from` — and repro mode with them — are planned for a later release. This release delivers labs from the installed catalog and from directories you author.
- **No certified concurrency.** One instance at a time is what this release certifies. You *can* start more; the isolation proof is planned for a later release.
- **No catalog listing command.** `podaro catalog` is not built: browsing and searching the installed catalog is planned for a later release. `system install` extracts the starter catalog, `lab plan` reads a template, and `up` on a name that is not installed refuses with the installed names on its cause line.
- **No instance-scoped diagnostics.** `podaro doctor` reads the host. A per-instance `doctor <instance> --check <x>` and its `POST /system/doctor` route are documented and unrouted, and no phase has claimed them yet; a lab's own account is `podaro logs` and its Evidence tab.
- **No catalog or authoring HTTP surface.** `GET /catalog/*`, `POST /lab/validate` and `POST /lab/plan` are documented and unrouted; the CLI does that work locally. Remote authoring arrives with `publish`, in a later release.
- **No job cancellation.** `destroy` is the off-switch; safe cancellation is planned for a later release.
- **No strict gating, no scoped resets.** Gating is soft — a red step stays visibly red and you may continue. Reset is full-to-baseline.
- **No ACME, no appliance image, no multi-user anything.** Bring your own certificate or use the generated local CA; the wildcard leaf re-issues itself. The appliance and ACME come later.
- **No release signing yet.** Sigstore is on the roadmap. Until then the verification path is `SHA256SUMS` and a deterministic build: `hack/release_package.sh` builds the same bytes twice and proves it, so anyone can rebuild the release from its commit and compare digests.
- **No AI in the runtime.** `explain` reads embedded metadata offline. The authoring and MCP lanes are planned for a later release, and the platform stays fully operable with no model configured, by invariant.

**Retired before the release.** On 2026-09-23 the project retired its original lab and the integrations dedicated to it, and on 2026-09-24 they left the tree and the binary, before any release: the lab's template and playbook, its five product modules, the three product query adapters and the three composites over them, the two generators made for it, the stand-in product behaviours its tests used, its scenario asset, and its end-to-end script. Nothing in this release restores, hides or offers any of it. A manifest that names a retired adapter, generator or module fails validation with `PDR-E106` (`400`) under either contract version; `podaro up` or `podaro lab init --from` the retired template's name is refused with `PDR-E107` (`404`) before anything is validated — `podaro explain` expands both. A host a development build ran before then may still hold that template in its catalog, or an instance of it: this release keeps both and operates neither — the entry is never offered, the instance is never reconciled, repaired, restarted or stopped (`PDR-W103`), every operation that would run its lab is refused with `PDR-E215` (`409`), its status, evidence and reports still read, `podaro destroy` is the one act that removes it, and `podaro system upgrade` lists both before it replaces anything. The contract revision is why templates, modules, playbooks and checkpoints are `v1alpha2`, with `v1alpha1` read. The installer no longer changes a kernel value for it, and the doctor row that reported one is advisory.

**How it is verified.** Every step's acceptance is a script in `hack/`, and CI runs all of them on every pull request: the interrupt and reboot tests, the gateway curl matrix, the create path with its secret-leak scan, the exec conformance fixture under rootless Podman, the console walked in a real browser, the licence gate and `PDR-W101` on first-party fixtures, every retained built-in adapter and generator on vendor-neutral services, the attendee matrix, the observability export against a collector and a mock HTTP Event Collector, `system upgrade` against a real release mirror laid out at the path of the project's releases and, with no `--from`, against their own address answered on the host, the lab gate on every catalog template, schema self-validation, scenario YAML, the dependency-licence allowlist, every tracked file's licence, the third-party notices held to their sources, the release's legal files on the tarball, the bare binary and the public page, a neutral-name build that moves nothing but the name, the retirement and identity guards over the tree, the binary, the release, the CLI's output and the rendered console, and every link in the documents, with the repository's coordinates spelled as `SOURCE` and `go.mod` spell them. What no script can prove — real Podman, real image pulls and boot timings, a real browser trusting a real certificate — is what the acceptance log covers.

**Licensing.** Every first-party file — the engine, CLI, console and gateway, the schemas and specifications, the starter template and its modules, the scripts and the documentation — is `AGPL-3.0-only`, declared by its SPDX header or by `REUSE.toml`, with no copyright line; `NOTICE` states the project's qualified copyright position and, separately, the licensing grant. Current first-party releases use AGPL-3.0-only, subject to disclosed upstream and historical rights; third-party material keeps its own licences and notices, gathered in `THIRD-PARTY-NOTICES.md`. The name is covered separately by `TRADEMARKS.md`, a proposed policy: the licence grants no trademark rights beyond what applicable law permits, and nothing claims a registered mark. Every contribution carries a DCO sign-off, which attests the right to submit it under the project license and is not a copyright assignment.
